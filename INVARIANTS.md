# Invariants — AESOP

Hard rules every methodology in this repository holds. When a procedure, schema, template, prompt or example disagrees with one, the invariant wins and the other is the bug to fix. A methodology's own `INVARIANTS.md` holds the rules specific to it; this file holds the ones that bind all of them.

- **A methodology holds what any instance would do; what one instance decides is that instance's data.** A rule that fits only one person, company or occasion is a prompt for that instance, not method. A choice another user would make differently (which of two figures stands, what stays off a page, what to do where the instance has said nothing) is kept in the instance's own working folder, outside this repository, and the methodology says where in that folder each such choice is read from, so a writer meeting a gap has a place to put the answer other than the procedure. First case: HIRE's smallest-figure default, a writer's own conservative guess for one candidate written into the procedure as every candidate's rule, which put smaller figures on the candidate's documents than the ones the candidate had approved.
- **A methodology stands alone.** No methodology assumes another exists: each methodology's folder can be worked by a consumer who uses no other, and this repository has no concept of one methodology depending on another. Some are designed to work together, and no dependency follows from that: where two may share a consumer's working folder, each claims its own files and says in its own terms what it reads, and a file or folder name both use is the same by design, never by accident. Making one methodology depend on another is the owner's move; until the owner makes it, every methodology is written to be worked alone. First case: SIFT and HIRE, each written to say that HIRE's record of the candidate is the profile SIFT scores against, so that a consumer's file serving HIRE alone read as a breach of the method.
- **A methodology runs under the consumer's own profile.** No step a consumer runs requires a session outside the profile their sessions ordinarily use: no clean room or sealed room built on a second profile, a second sign-in or a token made for it. Such a profile goes stale, is made for one use and left behind, or is picked up by a mechanism it was not made for; its sessions are separate runs, unreliable when the profile fails, whose cost is reported against the user and not against the methodology's run. A fresh agent under the consumer's own profile, given only part of the material, is not such a room. Where a step is held to need one and nothing else will do, the exception is the owner's to grant and is entered in this file. The rule binds what a consumer is asked to do; an author testing a methodology may use such a room. First case: HIRE's Examine, which chose between versions with sealed-room judges through a skill that signs in with a token the consumer creates, and a spare profile kept for such rooms that was found signed out when it was next needed.
- **A methodology's syntax names the role, not the business.** A field name, a closed-vocabulary value, or a string the tooling emits into a prompt names the part a value plays in the method, never the trade of the instance supplying it, and it does not presume that instance exists physically: a business with no premises, no visitors and no address runs the same schema as one with a street door. Instance data belongs to the instance; the vocabulary belongs to nobody. Two things this rules out, because a rename fixes only the first: a name answerable by one industry alone, and a slot only a business with a place can fill. First case: `venue`, an address and coordinate block in SPAR's campaign schema, deleted rather than renamed.
- **A case carries what its failure turned on, and no other trace of the instance.** A methodology's `cases/` records the incidents its rules came from, in a public repository, so the travellers or parties are named by role or an invented name, a date appears only when the failure depended on it (travelling over Christmas) and is otherwise left out rather than altered, and a place appears only when checking the case needs it, at the coarsest grain that still lets someone check it; booking references, addresses and contact details never appear. The case names the rule it produced, and the rule may cite the case. First case: travel's early failure write-ups, filed with the family's names, ages, booking references and a health constraint, and removed from the whole history on 12 November 2026.
