# The frame-uniform family (`frame_size`, `screen_curvature`, `screen_radius`, `frame_shininess`, `ambient_light`)

None of the eight "homes" is a reimplemented function — each is `pub frame_size` (or sibling) as a plain field on an unrelated struct: `ChassisSettings`/`ScreenSettings` (config/schema.rs, two structs), `DistortionParams` (term/distortion.rs, f64), a second `DistortionParams` in crt-render/src/oracle.rs (f32, CPU oracle for `terminal_frame.slang`), a third in chassis/src/oracle.rs (f32, CPU oracle for `frame_metal.slang`), `FrameScale` (chassis/frame.rs), and three near-identical `FrameRuntime` carriers, one per shell (annunciator.rs, slide_rule.rs, switchboard.rs). The count is real, not an artefact of the grep — but it is not eight independent decisions either. The two oracle duplications are deliberate and doc-justified: `terminal_frame.slang` and `frame_metal.slang` each carry their own copy of `distort_coordinates`, the Rust oracles mirror that split because the chain crate and the chassis crate cannot see each other, and a cross-crate test in app/tests/structure_subset.rs pins the two derivations to the same answer. The three `FrameRuntime` structs are plain pass-through carriers with identical fields, not re-derivations.

**The path a value takes**: `[chassis]`/`[screen]` TOML → `ChassisSettings`/`ScreenSettings` field → `Config::raw_frame_size()` (chassis-or-screen split, config/lib.rs) → two independent consumers that must agree: (a) `crt-render::params::Params::build` computes `frame_size = raw * 0.05 * normalized` and pushes both `FrameSize`/`frameSize` uniforms, checked against crt-render/src/oracle.rs's own copy; (b) `chassis::frame::FrameScale::build` computes the same product for the bezel pass, pushed through `frame_params`, checked against chassis/src/oracle.rs, and fanned out again into the three shells' `FrameRuntime`. A ninth path exists purely for the pointer: `app::settings::distortion_frame_size` inverts the same arithmetic for `term::distortion::DistortionParams`.

Adding one new setting of this shape costs on the order of **11–13 edits**: schema field(s), all 13 preset literals in config/presets.rs, config/structural.rs's `STRUCTURAL` list (if it resizes anything), a `raw_*` accessor, the two `params.rs`/`frame.rs` computations, their two oracle mirrors, and the three shell `FrameRuntime` structs. The repo already tracks this: crates/xtask/src/fanout.rs exists expressly for GitHub issue #4, "the setting-duplication report," and `xtask fanout frame_size` (run here) returns 62 non-test lines across 14 files. **Verdict: scattered** — real mechanism, ~12 edit sites for one new setting, though several of the homes (the two shader-language oracles) are individually justified and test-guarded rather than accidental.

`screen_curvature`, `screen_radius`, `frame_shininess`, `ambient_light` are the same pipeline, same verdict, same cost order (fanout: screen_curvature 42 lines/14 files reported by the audit table; not separately re-run).

# The chassis measure contract (`unit_width`/`min_units`/`width_for_units`/`height_for_pad_cells`)

These are a `pub trait DisplayMetrics` (chassis/metrics.rs) with two real implementors, `LedMetrics` and `TapeMetrics`, each delegating to a free formula function of the same name in its own `displays/{led,tape}/metrics.rs`. `cabinet.rs`'s `Display` enum match arms and `bank.rs`'s field-copy are call-sites/carriers, not redefinitions. **Verdict: by design** — a sibling-module interface (the doc in metrics.rs explicitly names the struct/trait split as intentional).

# `pixel_size`

One value, computed once in term/fonts/sizing.rs, then threaded as a same-named parameter/field through metrics.rs → led.rs → text.rs (font rendering pipeline) and separately used with an unrelated meaning in chassis/paint.rs (a paint operation's stamp size). No independent re-derivation found. **Verdict: by design** — shared vocabulary for a value passed down a pipeline, not decided N times.
