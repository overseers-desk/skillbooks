# Audit brief: how much of one SAGE run would have to be done again

You are auditing one finished or part-finished SAGE run, to estimate how much of its work would have to be done again to bring its conclusions up to the method as it now stands. This is a read-only audit: edit nothing and commit nothing.

**The method** is at `/usr/local/src/aesop/pmf-sage/`: `sage-methodology.md` first, then the four phase documents, `forms/` and `tools/`. **What changed and why** is in `sage-change-digest.md` beside this brief. Read both before the run.

**The run** is named in your prompt, under `/usr/local/src/rivermill/product-development/`. Run folders are large (hundreds of files); the README or run record, the `briefs` folder, the blacklist or fence folder and the decisions folder are the quickest way in.

## Questions to answer from the run's own files (path and a short quotation for each)

1. Which phases did the run reach, on what dates, and is the offering already on sale or otherwise acted on (README, run record, product definition, booking-system descriptions, anything in the product folder beside the run)?
2. Who chose the buyer, and when? Find the earliest brief or frame document that names a buyer or fixes how many offerings there are, and say whether a dated owner ruling stands behind it.
3. Did any agent that derived frames, the codebook, cards or designs read the venue's own drafts, its present practice, or another run? The run's blacklist or fence folder and the briefs' read lists show this.
4. For the decision cards: how many options carry a figure on each; how many recommendations equal a value an internal document already held (name the document); where an enquiry count serves as a demand leg, what condition is stated beside it.
5. Does the run hold any finding on what buyers type into a search engine?
6. For Game and Establish work: which card rulings does each judged design, definition or claim rest on?

## The estimate

Split the run's work into blocks, for instance: frames and source lists; codebook; collection; coding and reliability; findings; rival register and demand record; capability note; cards and owner review; design arms, reviewer and judges; absorption; definition and claims. Use the blocks the run actually has. Give each block its share of the run's total effort, summing to 100, judged from the files (file count and size are a fair proxy; say what you used). Give each block one verdict:

- **STANDS**: usable as it is under the current method.
- **REUSE**: the material stays and a new step reads it (name the step), for example collected pages coded again for a new variable.
- **REDO**: has to be done again; name the fault that makes it so.
- **CONDITIONAL**: stands only if the upstream work it rests on, once redone, lands where it did; name the upstream block.

List separately, as **NEW**, the work the current method requires that the run never did, sized as a percentage of the run's original effort.

## What to return (under 700 words)

- One line: run, start date, phases reached, on sale or not.
- A table of blocks: share, verdict, one-line reason with a path.
- Totals: STANDS, REUSE, REDO and CONDITIONAL as percentages of the original effort, summing to 100; NEW as a separate percentage.
- The three facts that most drive the estimate, each with its path and quotation.
- What you did not read, and your confidence in the totals (high, medium, low).

Report what the files show. Where a verdict turns on a judgment call, say which way you called it and what would flip it.
