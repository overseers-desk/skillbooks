This is a Kahneman's system 2 question. The sections of the office methodology that bear on it are "Version control and issue maintenance" (which itself carries the `--only` rule: "commit with `--only` to stage whole files touched this conversation") and, for the style of the reply, "Writing for a reader"; I have re-read both in context.

Here is everything the hook message teaches me, as I understand it.

**What it requires, and of whom.** It binds the AI session that receives it (me), working in a git checkout that is shared: several sessions, human or AI, may have work in progress in the same working tree at once. The requirement is that when this session commits, it must use `git commit --only <files>`, naming exactly the files this conversation touched, as whole files, and nothing beyond them.

**What it forbids.** Any blanket staging operation: `git add -A`, `git add --all`, `git add -u`, `git add .`, and `git commit -a`. The stated reason is that these sweep into the commit whatever sibling sessions have left in the working tree, both their work in progress and their scratch files.

**The inspection duty.** Before building on existing staged or committed state, the session must list what is staged or what the last commit contains, using `git status` for the index and `git show --stat HEAD` for the tip commit, and must be able to claim each listed file as this session's own work. If some file cannot be claimed, the remedy depends on where the stray content sits, and I read the three remedies as mapped to three situations: unstage it if it is only in the index; amend the commit if it is in HEAD but not yet pushed; revert if the commit carrying it has already been pushed.

**The exceptions.** Two situations restore permission to stage broadly: the user has explicitly ordered a sweep (told the session to stage everything), or the material is a fresh import that is wholly this session's own, such as a new directory of files the session itself created, where there is nothing of anyone else's to sweep.

**What satisfies it.** A commit made with `git commit --only a.py b.md -m ...` where `a.py` and `b.md` are the files this conversation edited or created; an amend or a build-on-HEAD done only after listing the staged or committed files and confirming each one is this session's; a blanket add done under one of the two exceptions.

**What violates it.** Any of the blanket forms outside the exceptions; committing a file the conversation never touched; amending or stacking commits on top of state containing unclaimed files without first unstaging, amending, or reverting; and, once a sweep of someone else's work has been pushed, leaving it in place rather than reverting.

**Why it exists, as far as I can tell.** The office runs multiple concurrent sessions against one checkout. Git's index and working tree are global to the checkout, not per session, so any staging command that selects by pattern rather than by name will capture other sessions' half-finished work and destroy the correspondence between a commit and the conversation that produced it. `--only` bypasses the shared index entirely by naming files, so each commit records exactly one session's contribution. The inspection duty covers the complementary hazard: another session (or a past mistake) may already have polluted the index or HEAD, and building on it uninspected adopts the pollution as one's own.

**What I would do on receiving it.** Work normally; at commit time, enumerate the files this conversation touched and commit them by name with `--only`; never run a blanket add or `commit -a` unless the user orders it or I am importing something wholly mine; before any amend or before treating pre-existing staged content as mine, run `git status` and `git show --stat HEAD`, check each file against what this conversation actually touched, and clean out anything unclaimed by the remedy appropriate to where it sits.

**Parts that are unclear to me.** Three points. First, the antecedent of "it" in "Before building on it" is not explicit; I take "it" to be the existing staged or committed state, since the two listed commands inspect the index and HEAD, but the sentence does not say so. Second, the clause "otherwise unstage, amend, or revert already-pushed commits" compresses three remedies and their triggering situations into one list; my mapping of unstage-to-index, amend-to-unpushed, revert-to-pushed is an inference from git mechanics, not something the sentence states. Third, "whole files" leaves one real case unaddressed: if a sibling session and this one have both edited the same file, `--only` commits the whole working-tree version of that file, sweeping the sibling's hunks along with mine; the message gives no instruction for that collision.
