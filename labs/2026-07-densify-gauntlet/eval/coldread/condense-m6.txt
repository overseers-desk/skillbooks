This is a Kahneman's system 2 question. The methodology sections that bear on it are "Writing for a reader" (the cold-reader discipline and the sorry-im-late skill, which this hook message operationalizes for issues) and "Version control and issue maintenance" (what an issue body is for: the live work in its current shape, readable without the conversation). I have re-read both.

What follows is my reading of the hook message, stated as data.

**What it requires, and of whom.** It requires the agent in the session (me, or any Claude session where the hook fires) to run the /sorry-im-late skill on a draft GitHub issue before the issue is created. The requirement falls on the AI, not the human user: it is injected into a session and phrased as an instruction to the party composing the `gh` command.

**In what situation.** When a GitHub issue is about to be created from material drafted during a conversation, that is, when the issue text was written mid-session and is therefore at risk of reading like the tail of that session. The message's own theory of the situation: a contributor who has the repository but not the exchange cannot resolve conversation-internal references such as "Option C", "the current behaviour", or decisions whose justifications were spoken but never written down.

**What the mechanism is.** The /sorry-im-late skill spawns a fresh agent that has the project's context (the repo) but none of the conversation's context. That agent reads the draft and queries every reference it cannot resolve. The author then folds the answers into the draft, so each formerly conversation-relative reference becomes self-contained. This is a blind-test design: the cold reader simulates the future contributor, and the author cannot self-certify because authors cannot see their own context leakage.

**What satisfies it.** Running the skill on the draft, incorporating the cold reader's answers into the issue text, and then issuing the `gh` command with `SORRY_IM_LATE_DONE=1` prepended (as an environment variable on the command line). The variable is the attestation that the pass happened.

**What violates it.** Creating the issue without running the skill; running the skill but not folding the answers in before creating; or prepending `SORRY_IM_LATE_DONE=1` without having actually done the pass, which would defeat the mechanism while satisfying its letter. The message's final clause, "the block forces one deliberate pass," implies the hook system blocks a bare `gh issue create` and that the variable is what lets it through; falsely setting the variable is therefore the salient cheat.

**Why it exists, as far as I can tell.** It mechanizes the cold-read discipline for one specific artifact class. An issue body must state the live work so a stranger can act on it (the standard stated in the methodology's issue-maintenance section), but an issue drafted mid-conversation naturally inherits the conversation's vocabulary and elisions, and the author cannot detect this from inside the conversation. The enforcement shape, a block that must be consciously bypassed with a marker, exists because a purely advisory reminder would be skipped under momentum; requiring the prepended variable guarantees at least one deliberate moment of deciding "yes, this issue stands alone" before the command runs.

**What I would do on receiving it.** On preparing to create a GitHub issue, I would first invoke the sorry-im-late skill on the draft body, let the fresh agent surface every unresolvable reference, rewrite the draft so each is answered in place (naming what "Option C" is rather than citing it, stating the current behaviour rather than pointing at it, writing down the reason for each decision), and only then run the creation command with `SORRY_IM_LATE_DONE=1` prefixed. If the hook had already blocked a first attempt, I would treat the block as expected behaviour rather than an error to route around, and would not set the variable without having done the pass.

**Parts that are unclear or that I am inferring rather than reading.** Two inferences: first, the word "recreate" implies the original `gh issue create` attempt is blocked by a hook and must be reissued, but the message never states outright that a block occurs or which hook enforces it; I infer it from "recreate" plus "the block forces one deliberate pass". Second, whether the hook actually verifies that the skill ran, or whether `SORRY_IM_LATE_DONE=1` is an unverifiable honor-system attestation, is not stated; the phrase "forces one deliberate pass" suggests the latter, that the variable's function is to make skipping a conscious act rather than to prove compliance. One scope ambiguity: the message covers issue creation only, and says nothing about whether issue comments, body edits, or PR bodies fall under the same requirement. Nothing in the message is unintelligible to me beyond these points.
