This is a Kahneman's system 2 question. The methodology sections that bear on it are "Handling the request and executing the plan" (subagent tiers, NQA, the shift/clock-off mechanism) and the cue-word conventions at the top of the methodology; I have re-read them in context.

What follows is my understanding of the hook message, stated as raw data.

**What kind of message it is.** It is the output of a hook in the plugin, almost certainly a PreToolUse hook watching the Agent tool. The phrase "Rewrite the spawn prompt with the ceremony and retry" implies the hook blocked the Agent call rather than merely advising; `{missing}` is a template placeholder the hook fills with whichever required parts were absent from the spawn prompt it inspected.

**When it applies.** Only "during a shift" — the state armed by the holotapes:shift skill for an unattended run, which creates an orders file and is closed later by clock-off. Outside a shift the requirement does not exist and the hook presumably does not fire.

**Of whom it requires something.** The orchestrating session (the one calling the Agent tool). It imposes one obligation at spawn time and one ongoing obligation.

**What satisfies it at spawn time.** Every Agent spawn prompt must open with a CEREMONY block containing two parts. Part one: the chosen model tier, from the set fable/opus/sonnet/haiku, together with a justification tying that tier to the complexity of the delegated work. This mechanizes the methodology rule that subagent tiers follow the component's consequence-of-error and complexity, not the conversation's altitude. Part two: a ledger clause, an instruction to the subagent that its final message must close with LEDGER entries covering two categories — gaps between the project goal and the current plan, and work surfaced while executing (dependencies, forgotten pieces) — or the literal word "none" when there is nothing to report. The "none" option makes absence of findings explicit rather than silent.

**The ongoing obligation.** When subagents return, the orchestrator collects their reported LEDGER entries into a file named ledger.md, located beside the shift's orders file. The hook message does not specify ledger.md's internal format; I would append entries in whatever form the shift skill's documentation prescribes, or plainly if it prescribes none.

**What violates it.** Spawning a subagent during a shift with no CEREMONY block; a block missing either part (tier without justification, or no ledger clause); retrying the blocked call verbatim; and, on the ongoing side, discarding reported LEDGER entries instead of writing them to ledger.md.

**Why it exists, as far as I can tell.** During a shift the user is asleep or away, so two things that would normally surface in conversation are otherwise lost. First, model-tier choice: unattended orchestration tends to reuse the orchestrator's own tier reflexively; forcing a written justification makes the choice deliberate. Second, the ledger: subagents notice plan-goal gaps and forgotten dependencies mid-execution, and with nobody watching, those observations evaporate unless a mechanism carries them to a durable file. ledger.md accumulates them beside the orders file so the morning review (clock-off) finds them. This is the shift skill's mechanization of the methodology's "batch the open questions for when the user wakes."

**What I would do on receiving it.** Read `{missing}` to see which parts were absent, rewrite the spawn prompt so it opens with a CEREMONY block containing both parts, re-issue the same Agent call, and from then on include the ceremony in every spawn for the rest of the shift. When each subagent's final message arrives, extract its LEDGER entries (including explicit "none"s, or at least the non-empty ones — the message does not say whether "none" is recorded or skipped; I would record something either way so coverage is auditable) and write them into ledger.md beside the orders file.

**Parts I cannot fully resolve from the message alone.** Whether the literal heading "CEREMONY" is required or only the content; whether "none" entries are themselves written to ledger.md; the exact location of the orders file (defined by the shift skill, not by this message); and whether the requirement covers Workflow-spawned agents or only direct Agent tool calls. None of these blocks compliance — the safe reading is literal heading, record everything, and apply the ceremony to any subagent spawn.
