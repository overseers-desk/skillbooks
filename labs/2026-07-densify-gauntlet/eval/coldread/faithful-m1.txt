This is a Kahneman's system 2 question. The methodology sections that bear on it: Handling the request (NQA and the shift skill), the subagent-tier rule ("Subagent tiers follow the component's consequence-of-error and complexity"), and the hook-advisory conventions (III); I have re-read them in context.

What follows is my full reading of the hook message.

**What kind of thing it is.** It is a hook rejection message, emitted by one of the plugin's hook scripts into a running session. The `{missing}` is a template placeholder the script fills at emission time with the name(s) of whichever required element was absent, so the live message would read something like "missing: ledger clause" or "missing: model-tier judgment, ledger clause". The final sentence, "Rewrite the spawn prompt with the ceremony and retry," tells me the hook fired on (and presumably blocked or flagged) an Agent tool call, most plausibly a PreToolUse hook matching the Agent/Task tool. It is a gate with a repair path, not a permanent denial: the same spawn is expected to be retried once the prompt is fixed.

**When it applies.** During a "shift" — the unattended-run mode armed by the holotapes:shift skill (/shift when the user leaves, /clock-off on return). The phrase "Every shift Agent spawn prompt" scopes the requirement to subagent spawns made while a shift is live. Outside a shift, this hook presumably does not fire, and the ceremony is not required.

**Of whom.** The orchestrating session — the agent calling the Agent tool during a shift. Two obligations fall on it, and one derived obligation falls on the subagent via the prompt it is given.

**What it requires.**

1. The spawn prompt must *open* with a CEREMONY block. Position matters: "opens with", not "contains".
2. The block has two mandatory parts:
   - *Model-tier judgment*: name the tier chosen for the subagent (fable, opus, sonnet, or haiku) and state why the work's complexity suits that tier. This mechanizes the standing office rule that subagent tiers follow the component's consequence-of-error and complexity, not the conversation's altitude — the hook forces the judgment to be written down rather than defaulted.
   - *Ledger clause*: an instruction to the subagent that its final message must close with discovered-work LEDGER entries in two parts. Part 1: gaps between the overall project goal and the current plan. Part 2: work that surfaced while executing — dependencies, forgotten pieces. If nothing was discovered, the subagent writes "none" rather than omitting the section.
3. After the subagent returns, the orchestrator collects any reported ledger entries into the shift's `ledger.md`, which lives beside the shift's orders file (an artifact the shift skill creates; I know of it only from this message and the skill's existence).

**What satisfies it.** A spawn prompt whose first block is the CEREMONY, containing both an explicit tier-plus-rationale statement and the ledger instruction with the "none" fallback; and, on the orchestrator's side, actually appending returned entries to ledger.md rather than letting them die in the subagent's final message.

**What violates it.** Spawning without the block; including only one of the two parts; burying the block mid-prompt instead of opening with it; a tier named without a why, or a why that argues from the conversation's importance rather than the delegated work's complexity; a ledger clause that lets the subagent silently skip the section; collecting nothing into ledger.md when entries were reported. Also, on receiving this message, retrying the identical prompt verbatim rather than rewriting it.

**Why it exists, as far as I can tell.** A shift is unattended: the user is asleep or away and cannot catch either failure this ceremony targets. The tier judgment counters the recurring offence the methodology names — reaching for the orchestration-level model for trivial work (or an undersized one for consequential work) without thinking, which unattended runs make expensive and invisible. The ledger counters silent loss of discovered work: mid-execution a subagent notices a dependency, a gap in the plan, or a forgotten piece; with no user present to tell, that discovery would otherwise evaporate when the subagent's context ends. Forcing it into a structured closing section, and forcing the orchestrator to persist it to ledger.md, gives the morning review (/clock-off) a durable record of everything the night's work surfaced but did not do. The "none" requirement makes absence an explicit claim rather than an ambiguous omission — the same absence-of-evidence versus evidence-of-absence distinction the densify rule protects.

**What I would do on receiving it.** Read `{missing}` to see which part(s) failed. Rewrite the Agent spawn prompt so it opens with a CEREMONY block: first the tier I chose and a one-or-two-sentence justification tied to the delegated task's complexity and consequence of error; then the instruction that the subagent close its final message with the two-part LEDGER (or "none"). Then reissue the Agent call. When the subagent returns, read its LEDGER section and append any entries to the shift's ledger.md next to the orders file, then continue. This retry is the sanctioned repair path the hook itself prescribes, distinct from re-running a user-denied call.

**Ambiguities I note plainly.** (1) The sentence "Collect reported entries into the shift's ledger.md" is addressed to the orchestrator, not text to embed in the subagent's prompt; the message's grammar does not mark that boundary, but the reading where the subagent writes ledger.md itself would break subagent isolation, so I take it as the orchestrator's job. (2) The exact hook event (PreToolUse block versus post-hoc advisory) is inferred from "retry", not stated. (3) The location and format of the "orders file" and of ledger entries within ledger.md are assumed known from the shift skill; the message does not define them. (4) Whether "fable" is a permissible tier for subagents generally or listed only for completeness is not stated. Nothing in the message is unintelligible to me beyond these underdetermined details.
