This is a Kahneman's system 2 question. The sections that bear on it are "Handling the request and executing the plan" (subagent tiers follow the component's consequence-of-error and complexity; NQA and the shift skill mechanizing the unattended floor) and the delegation guidance on briefing subagents; I have re-read them in context.

What follows is my full reading of the hook message.

**What kind of message it is.** It is a rejection notice from a hook in the plugin, emitted when an Agent tool spawn was attempted during a shift and the spawn prompt lacked a required preamble. `{missing}` is a template placeholder; in a real firing it would name which required piece or pieces were absent (the model-tier judgment, the ledger clause, or both). The message ends with a directive, so the spawn is understood to have been blocked or to not count: the correct response is to rewrite and retry, not to proceed.

**Of whom it requires what.** The obligation falls on the orchestrating session (the one calling the Agent tool), not on the subagent. It applies only during a shift, which in this plugin is the armed unattended-run mode entered via the shift skill and closed by clock-off. During a shift, every spawn prompt must open with a block labelled CEREMONY containing two parts.

Part one is a model-tier judgment: the prompt names the tier chosen for the subagent (fable, opus, sonnet, or haiku) and states why the work's complexity suits that tier. This mechanizes the standing rule that subagent tiers follow the component's consequence-of-error and complexity, not the conversation's altitude. Writing the judgment into the prompt forces the choice to be made deliberately and leaves an auditable record of it.

Part two is a ledger clause: an instruction to the subagent that it close its final message with LEDGER entries of discovered work, in two categories — (1) gaps between the project goal and the current plan, and (2) work that surfaced while executing, such as dependencies or forgotten pieces — or the literal word "none" if there is nothing to report. This part of the ceremony is addressed to the subagent; the tier judgment is addressed to the record.

**A follow-on duty for the orchestrator.** "Collect reported entries into the shift's ledger.md beside its orders file" means that when a subagent returns, any LEDGER entries in its final message are to be appended to a file named ledger.md that sits in the same directory as the shift's orders file. The orders file is an artifact of the shift skill; this message assumes I know where it is from having armed the shift. The ledger is therefore an accumulator across all subagents of the shift.

**What satisfies it.** A spawn prompt whose opening is a CEREMONY block containing both the tier judgment (tier named, suitability reasoned) and the ledger clause (the two-part LEDGER instruction with "none" as the empty case), followed by the task brief. Faithfully copying returned LEDGER entries into ledger.md satisfies the collection duty.

**What violates it.** Spawning during a shift with no CEREMONY block; a block missing either part; naming a tier without the reasoning, or reasoning without naming the tier; omitting the "or none" escape so the subagent cannot report cleanly when there is nothing; and, downstream, discarding reported entries instead of writing them to ledger.md. Outside a shift, none of this applies.

**Why it exists, as far as I can tell.** A shift runs while the user is away, under NQA-like conditions: questions cannot be asked and observations cannot be handed over live. Subagents routinely notice things tangent to their brief — a dependency nobody planned for, a gap between the plan and the goal — and in an attended session those surface in conversation; in an unattended one they evaporate when the subagent's context ends. The ledger clause harvests them into a durable file for the morning review at clock-off. The tier judgment exists because the recurring offence, named in the methodology, is spending the orchestration-tier model on work a cheaper tier should do (or the reverse); forcing a written justification per spawn interrupts that reflex during exactly the period when nobody is watching spend.

**What I would do on receiving it.** Take the spawn as not having happened. Read `{missing}` (in a real firing) to see which part was absent. Rewrite the spawn prompt so it opens with a CEREMONY block: first the tier I chose and why this component's complexity and consequence-of-error suit it, then the instruction that the subagent end its final message with the two-part LEDGER (or "none"). Retry the spawn. On the subagent's return, extract its LEDGER entries and append them to ledger.md next to the shift's orders file, then continue the shift's work.

**Parts I cannot fully resolve from the message alone.** First, whether "opens with" demands the CEREMONY block be the literal first text of the prompt or merely appear near the top; I would treat it as literal-first to be safe. Second, the exact on-disk format of a ledger.md entry (one line per entry? attributed to the spawning agent?) is unspecified; I would keep entries as reported, grouped by the two parts, and would expect the shift skill's own documentation to settle the format. Third, whether the requirement extends to agents spawned via the Workflow tool's `agent()` calls rather than the Agent tool; the message says "every Agent spawn prompt," which I would read broadly during a shift since the purpose (harvesting discovered work unattended) applies equally. Fourth, whether the tier named in the ceremony must be mechanically consistent with the `model` parameter actually passed to the Agent tool; the message does not say, but a mismatch would defeat the point, so I would keep them aligned. Nothing in the message is unintelligible to me; these four are underdetermined rather than opaque.
