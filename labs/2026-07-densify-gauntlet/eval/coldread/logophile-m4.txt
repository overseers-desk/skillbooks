This is a Kahneman's system 2 question. The methodology sections that bear on it are "Version control and issue maintenance" (the git-defaults reversal, of which this hook message is the enforcement arm) and "Anti-infantization" (the message uses "never", which per that rule must mean never). Both are already in my context; I have re-read them.

**Who it addresses and when it fires.** The message is addressed to the AI agent running inside a Claude Code session on a user's machine where this plugin is installed. It fires reactively: a hook has detected that the agent created a git branch named `{name}` during the current turn, and the message arrives after the fact, naming the branch it detected.

**What it teaches.** The Claude Code harness ships a default rule for commits: "If on the default branch, branch first." The message states that in this environment that default is inverted. The standing policy it announces has three parts. First, the agent should not branch before committing; commits go directly onto the default branch (main, in this repo). Second, the agent must not create a branch on its own initiative at all; a branch is legitimate only when the user explicitly asked for it. Third, "never" here is used in the invariant sense: the message allows no exception the agent may grant itself, only the exception the user grants by asking.

**What it requires right now.** The message asks the agent to classify the branch it just created. If the user, or a plan the user confirmed, called for a branch with this name, the creation was authorized and nothing further is required. If neither did, the creation is presumed habitual — the harness default firing out of place — and the required remedy is immediate and takes priority over all other work: delete the branch with `git branch -D {name}`, then make the intended commit on the default branch instead.

**What satisfies it.** Committing straight onto the default branch; creating branches only when the user asked for one; on receiving the message after an unauthorized branch creation, deleting that branch first and re-landing the work on the default branch.

**What violates it.** Creating a branch as a reflex before committing; keeping an unauthorized branch after receiving the message; continuing other work before resolving the branch; treating the harness's default rule as still in force.

**Why it exists, as far as I can tell.** The harness's branch-first default is trained into the agent and reasserted by the harness prompt every session, so the habit resurfaces even where local policy forbids it. This user's workflow treats the silent fork as the harm: an auto-created branch splits history without the user's knowledge, and work landed there is invisible from main and creates a merge the user never asked to manage. A hook is the right enforcement point because it fires deterministically at the moment of the offense, when the branch is empty or nearly so and `git branch -D` is cheap and safe. The message names the harness rule explicitly because the agent will otherwise resolve the conflict in the harness's favor; stating "that rule is INVERTED here" pre-empts that.

**What I would do on receiving it.** Check the conversation and any confirmed plan for an explicit request for a branch of that name. Absent one, run `git branch -D {name}` before anything else, confirm I am on the default branch, and commit the work there. Present, I would keep the branch and note the authorization. I would not re-create the branch later in the session without a user request.

**Ambiguities and edge cases.** Two points are underspecified rather than unintelligible. First, the message assumes the branch created this turn carries no commits unique to it; `git branch -D` (force-delete) would discard any commits already made on the branch and not merged. Since the hook fires within the turn of creation, the branch normally points at the same commit as its parent and deletion loses nothing, but the message does not say what to do if commits have already landed on the branch — the sensible reading is to move them to the default branch first, though the text does not state this. Second, "a confirmed plan" is not defined; I read it as a plan the user approved in this or a governing session, not a plan the agent formed alone. Nothing in the message is unintelligible to me.
