This is a Kahneman's system 2 question. The methodology sections that bear on it: "Version control and issue maintenance" (the git-defaults reversal, branch only on the user's word), the cue-word/III conventions (how hook advisories are meant to be judged), and INVARIANTS/obeying-invariants in "Handling the request" (a rule met mid-work is obeyed, not worked around). I have re-read them in context.

What the message teaches, as I understand it:

**Who it addresses.** The AI agent running the session — not the human user. It fires from a hook that detected a branch-creation event attributed to the agent within the current turn.

**The situation it fires in.** The agent created git branch `{name}` during this turn. The hook cannot know whether that creation was authorized, so it states a decision rule and a presumption.

**The rule it states.** In this environment, the harness system prompt's default guidance ("If on the default branch, branch first" before committing) is deliberately reversed. The standing rule is: the agent never creates a branch on its own initiative; a branch is created only when the user explicitly asked for one, or a plan the user confirmed called for it. Commits otherwise go directly onto the default branch.

**The presumption and the remedy.** Unless the just-created `{name}` was called for by the user or a confirmed plan, the message presumes the creation was habitual — the trained harness default firing rather than a decision. The prescribed remedy, to be done before any other work: delete the branch with `git branch -D {name}`, then make the commit(s) on the default branch.

**What satisfies it.** Either of two outcomes: (a) the branch was in fact explicitly requested — then keeping it satisfies the rule and no action is owed; or (b) it was not requested — then deleting it immediately and committing the turn's work onto the default branch satisfies it. Timeliness is part of compliance: the cleanup comes "before doing anything else."

**What violates it.** Continuing to work, commit, or push on the unsolicited branch; deferring the deletion until later in the turn; rationalizing the branch retroactively; or creating further unsolicited branches. Also, in future turns, following the harness default rather than this local inversion would violate the rule the message teaches, independent of the hook firing.

**Why it exists, as far as I can tell.** Agents are trained and system-prompted to branch before committing on a default branch, so they do it reflexively. This office's convention (recorded in the methodology's git section) is the opposite: commit straight onto the default branch; the thing guarded against is the silent fork, not the branch itself, and the user creates branches freely when they want them. A hook is the right mechanism because the habit fires at commit time regardless of what documentation says; the message intercepts the habit at the exact moment it manifests and prescribes the undo.

**What I would do on receiving it.** First check the conversation and any approved plan for an explicit request for `{name}`. If one exists, the hook has misfired against an authorized branch; per the judgment convention for hook advisories, I would keep the branch and proceed (silently, if the advisory carries the ignore-if-irrelevant convention; this message does not, so a one-line note that the branch was requested would be reasonable). If no request exists, I would check whether the branch carries commits not reachable from the default branch; if it does, I would bring them onto the default branch (switch to default and fast-forward or cherry-pick) before deleting, then run `git branch -D {name}`, and continue committing on the default branch.

**Ambiguities and one gap.** (1) "A confirmed plan" I read as a plan the user approved (e.g., an accepted plan-mode plan), not a plan the agent formed alone. (2) The ordering in the message — delete the branch, *then* commit onto default — is only safe when the branch has no unique commits (the common case: branch created, work still uncommitted, or HEAD unmoved). If commits already landed on the branch, `git branch -D` before securing them on default would leave them dangling (recoverable via reflog, but wrong as a procedure). I take the message's intent to be "the work belongs on the default branch; the branch pointer must go," and I would sequence the steps to preserve the commits. Nothing in the message is unintelligible to me beyond that ordering nuance.
