This is a Kahneman's system 2 question. The methodology sections that bear on it are "Version control and issue maintenance" (the reversed git defaults, specifically "Branch only on the user's word") and, secondarily, "Deciding what to build" (AAA/anti-infantization, since this is an instruction written for an AI reader); I have re-read them.

What follows is my full understanding of the hook message, written as raw data.

**Who it addresses and when it fires.** It addresses the AI agent in the session (me), and it fires reactively: the hook has detected that I created a git branch named `{name}` during the current turn. It is not a standing policy statement delivered at session start; it is a correction triggered by a specific action already taken.

**The policy it teaches.** The Claude Code harness's built-in default is "if on the default branch, branch first" before committing. This project (or the environments where the plugin is installed) inverts that default: commits go directly onto the default branch (main, typically), and creating a branch is the exceptional act, permitted only when the user explicitly asked for one, or when a confirmed plan (one the user approved) called for one. The bar is on the AI silently forking, not on branches as such.

**What it requires of me, concretely.** A conditional: first, check whether this specific branch was called for — did the user ask for it, or does an approved plan name it? If yes, the branch stands and no action is required. If no (I created it on my own initiative, most likely by reflexively following the harness default), I must undo it: delete the branch with `git branch -D {name}` and put my commits onto the default branch instead. "Before anything else" means this remediation takes priority over continuing whatever task I was doing; I do not stack more work on the unauthorized branch.

**What satisfies it.** Either (a) the branch is genuinely user-authorized or plan-authorized, and I leave it alone; or (b) it is not, and the end state is: the branch no longer exists, and the work I was about to commit (or had committed) on it now sits as commits on the default branch. Note the practical sequencing the message compresses: if I am currently on the branch, I must switch to the default branch first, since git refuses to delete the checked-out branch; if the branch already carries commits not on the default branch, I must carry them over (cherry-pick, merge, or reset-and-recommit) before or as part of deleting, because `-D` force-deletes without a merged-ness check and would otherwise strand those commits in the reflog. The message's phrasing "delete it and commit onto the default branch" implies the work is preserved and relocated, not discarded.

**What violates it.** Keeping a branch I created without an explicit ask; continuing to commit onto it; asking the user whether to keep it when nothing authorized it (the instruction is unconditional once the authorization check fails); or, conversely, deleting a branch the user did ask for (the "unless" clause exists precisely to prevent that over-application). Deleting the branch in a way that loses the commits would also violate the evident intent, since the instruction pairs the deletion with committing the work onto the default branch.

**Why it exists, as far as I can tell.** The harness default assumes a workflow where the default branch is protected and feature branches are the norm. This user's workflow is the opposite: they commit straight to main, in stages, and an AI-created branch is a silent fork — work parked somewhere the user will not look, diverging from where the user expects everything to land, creating merge debt and a half-synced state for whoever arrives next. The harness instruction is baked into the system prompt and reasserts itself in every session, so the plugin needs a hook that catches the moment the default wins over the project rule and corrects it immediately, while the branch is one turn old and cheapest to unwind. It teaches the inversion at exactly the moment it is violated rather than hoping the agent retained it from a document.

**What I would do on receiving it.** First recall whether the user or an approved plan asked for this branch in this conversation. If one did, I would note that authorization to myself and continue on the branch. If not, I would: check out the default branch, bring the work over (if the branch had commits, cherry-pick or otherwise replay them; if only working-tree changes, they follow the checkout), run `git branch -D {name}`, commit onto the default branch, and only then resume the task. I would not ask the user for permission to do this, since the hook message itself is the standing authorization.

**Unintelligible parts.** None of it is unintelligible to me. The only under-specified point is the mechanics of preserving already-made commits during the delete-and-recommit sequence, which the message leaves to the agent's git competence, and the phrase "confirmed plan," which I read as a plan the user approved (e.g. via plan mode or explicit assent in conversation), though the message does not define it.
