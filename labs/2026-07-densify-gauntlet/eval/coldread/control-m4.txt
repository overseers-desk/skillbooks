This is a Kahneman's system 2 question. The methodology sections that bear on it are "Version control and issue maintenance" (the git-defaults-are-reversed paragraph, specifically "Branch only on the user's word") and, less directly, "Handling the request and executing the plan" (a project rule met mid-work is obeyed, not worked around). I have re-read them; the hook message is a runtime enforcement of the first.

**What the message is.** It is emitted by a hook after the session has created a git branch during the current turn. `{name}` is interpolated with the branch's name. Its audience is the AI agent in the session where the hook fired, at the moment just after the branch creation.

**What it requires, of whom, in what situation.** It requires the agent that just created the branch to do two things. First, a policy correction: it declares that the Claude Code harness's baked-in instruction "If on the default branch, branch first" does not apply in this environment; the local rule is the opposite — commit directly onto the default branch, and create branches only when the user explicitly asks (the message body adds "or a confirmed plan called for this branch" as the second legitimate origin). Second, a conditional remediation: the agent must classify the branch it just made. If the user asked for it, or an approved plan called for it, the branch is legitimate and stands. If neither did, the branch is presumed habitual — the harness-trained reflex firing — and the agent must delete it with `git branch -D {name}` and commit its work onto the default branch, and must do this before any other work in the turn.

**What satisfies it.** Either outcome satisfies it: (a) the agent traces the branch to an explicit user request or a confirmed plan, keeps it, and continues; or (b) finding no such origin, the agent deletes the branch as its next action and commits onto the default branch. In case (b), "before doing anything else" means the remediation takes priority over whatever the agent was in the middle of.

**What violates it.** Keeping an unrequested branch; committing onto it; deferring the cleanup until later in the turn; inventing a retroactive justification for the branch (treating "I made it" as evidence it was wanted); and, prospectively, creating branches by reflex in future turns of the session. Silently reverting to the harness default because it is in the system prompt would also violate it — the message explicitly names and overrides that instruction.

**Why it exists.** The harness system prompt tells every Claude Code session to branch before committing on the default branch. That instruction is delivered to the model on every turn and the model tends to follow it reflexively. This user's workflow is the opposite — work lands as staged commits directly on the default branch, and an unrequested branch is a silent fork that fragments history. A CLAUDE.md sentence stating the reversal competes with the harness prompt at a distance; this hook instead fires at the exact moment of the offense, names the specific branch, and prescribes the undo. It converts a standing rule the model may have skimmed into a point-of-error correction it cannot miss.

**What I would do on receiving it.** I would check the conversation for an explicit user request or an approved plan step that called for a branch. Absent one, I would treat the branch as habitual: switch back to the default branch, delete the new branch, and commit the turn's work onto the default branch, then resume the task. Two mechanical details the message leaves implicit: git refuses to delete the branch you are currently on, so a checkout of the default branch must precede the `git branch -D`; and if I had already committed onto the new branch, `git branch -D` would strand those commits, so I would first bring them onto the default branch (for a branch just forked from the default's tip, resetting or fast-forwarding the default branch to the branch tip does this losslessly) and only then delete. I read "delete it now... then commit" as assuming the common case where the branch is fresh and the work is still uncommitted; where commits already exist, preserving them onto the default branch honors the message's evident intent (the work belongs on the default branch) better than a literal-order reading that would destroy them.

**Unintelligible parts.** None. Every clause parses. The only tensions are the two implicit mechanics above (cannot delete the checked-out branch; forced deletion versus commits already on it), which are gaps in stated procedure rather than unintelligibility, and the minor asymmetry that the imperative sentence says "unless the user asked for one explicitly" while the remediation sentence admits "a confirmed plan" as a second legitimate origin — I take the union: user request or confirmed plan legitimizes a branch.
