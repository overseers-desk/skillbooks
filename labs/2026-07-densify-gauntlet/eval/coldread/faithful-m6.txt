This is a Kahneman's system 2 question. The methodology sections that bear on it are "Writing for a reader" (the cold-reader/sorry-im-late discipline and forward-only) and the skill listing for skillbooks:sorry-im-late; I have re-read them in context.

What the message teaches me, as I understand it:

**Who it binds.** The agent in the session — me, or any Claude session running with this plugin's hooks — at the moment it is about to create a GitHub issue. It does not address the human user, though a human could follow the same discipline.

**The situation it targets.** An issue drafted during a conversation. Such a draft tends to contain references that resolve only inside that conversation: option labels coined in the chat ("Option C"), pointers to the discussion itself ("as discussed"), deictic phrases whose referent is the session's moment ("the current behaviour"), and decisions stated without the reasons, because the reasons live in the talk. The intended reader of the issue is a contributor who has the repository but not the conversation; for that reader these references are unresolvable.

**What it requires.** Before running `gh issue create` on such a draft, invoke the /sorry-im-late skill on it. The skill's mechanism is a cold-reader test: it spawns a fresh agent that knows the project (has the repo) but has none of this conversation's context, and that agent queries every reference it cannot close from the repo alone — i.e., every reference only the conversation can resolve. The drafting session then folds the answers into the draft, so the references are replaced by or accompanied by their referents. Then, and only then, the issue is created by re-running the gh command with `SORRY_IM_LATE_DONE=1` prepended — that is, as an environment-variable prefix on the command line: `SORRY_IM_LATE_DONE=1 gh issue create ...`.

**What is implied but not stated.** There must be a companion hook that blocks `gh issue create` when the marker variable is absent; "recreate the issue with SORRY_IM_LATE_DONE=1 prepended" only makes sense if the first, unmarked attempt is refused. "Recreate" therefore means re-issue the blocked creation command, not delete and re-file an issue that already exists on GitHub. The marker is not a secret or a security measure; the final sentence says so directly: "Working around the block is the point." The block is a tripwire whose entire function is to force one deliberate pass over the question "does this issue stand without the conversation?", and setting the variable is the agent's attestation that the pass happened. The gate is honour-system by design.

**What satisfies it.** The sequence: draft → run /sorry-im-late on the draft → receive the cold reader's queries → rewrite the draft so each conversation-only reference is closed (the option named as what it concretely is, the decision carrying its reason, "the current behaviour" replaced by a description of that behaviour) → run the creation command with the marker prefixed. Running the skill and finding nothing to fix also satisfies it; the requirement is the pass, not the presence of defects.

**What violates it.** (1) Prepending `SORRY_IM_LATE_DONE=1` without having run the skill — this passes the mechanical gate while defeating its purpose, a false attestation. (2) Running the skill but not folding the answers in before creating. (3) Creating the issue through some path the hook does not see (e.g., `gh api` directly, or the web) to dodge the gate. (4) Exporting the variable session-wide so every future issue sails through — an inference on my part, but it follows from the marker being a per-issue attestation; a standing export converts the deliberate pass into no pass. (5) Judging by eye that the draft "obviously stands alone" and skipping the skill: the message asks for the fresh-agent pass precisely because the author cannot see their own context-dependence.

**Why it exists.** It mechanizes the cold-reader discipline for one specific artifact class. An issue is a durable document addressed to a stranger-in-time; the author's session context evaporates, and every reference that leaned on it becomes dead weight or misdirection for the next reader (human or AI). The author is structurally the wrong judge of whether the draft stands alone, because they cannot un-know the conversation; hence the fresh agent, which is the only reader who can honestly report what fails to resolve. The block-plus-marker design exists because a purely advisory reminder would be skipped under momentum; a hard block with a self-set key costs one deliberate act, which is the minimum that guarantees the question was actually asked.

**What I would do on receiving it.** When I have an issue draft ready and am about to run `gh issue create`, I would first invoke the sorry-im-late skill with the draft as its input, wait for the cold reader's queries, rewrite the draft answering each from the conversation's knowledge, and then run the creation command once with `SORRY_IM_LATE_DONE=1` prefixed to that single command. I would not set the variable ahead of running the skill, and I would not export it.

**Parts I cannot fully resolve.** Two edges are underdetermined by the message itself. First, scope: it names issue creation only; whether the same gate covers issue comments, body edits, or PR bodies is not stated, and I would assume it does not unless the hook fires there too. Second, "the skill spawns a fresh agent that knows the project but not this conversation" — how the agent "knows the project" (working directory access, presumably) is mechanism internal to the skill and not something the message obliges me to know; nothing in the message is unintelligible beyond these.
