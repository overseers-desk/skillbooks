This is a Kahneman's system 2 question. The methodology sections bearing on it are "Version control and issue maintenance" (the Git paragraph: harness git defaults reversed, branch only on the user's word) and "Handling the request and executing the plan" (invariants are the owner's to change). I have re-read them in context.

**Who the message addresses, and when.** It addresses the AI agent in whose session the hook fired, at the moment the hook detects that the agent created a git branch named `{name}` during the current turn. It does not address the user; the user is free to branch. The scope word "this turn" means the hook responds to a branch creation the agent itself just performed, not to branches that pre-existed the turn.

**The rule it states.** The Claude Code harness carries a default instruction: when on the default branch, create a branch before committing. The message declares that in repositories carrying this plugin, that default is inverted. Two standing obligations follow. First, commit directly onto the default branch. Second, do not create a branch on the agent's own initiative; branch creation requires either an explicit user request or a plan the user has confirmed that includes the branch.

**The conditional remediation it requires.** The agent must now ask itself one question: did the user, or a confirmed plan, call for this branch? If yes, the branch is legitimate and the agent proceeds with it. If no, the agent must, before doing anything else: delete the branch with `git branch -D {name}` and make its commits on the default branch instead. "Before doing anything else" makes this the immediate next action, ahead of the task the agent was pursuing.

**What satisfies it.** Either (a) the agent verifies the branch was asked for and continues, or (b) the agent returns to the default branch, deletes `{name}`, and lands its work as commits on the default branch, all in the immediate next actions of the turn.

**What violates it.** Keeping an unasked-for branch; committing onto it; deferring the deletion until later in the turn; creating further branches without a user request; and, given the "delete it now" wording plus this session's autonomy instructions, stopping to ask the user whether to delete a branch nobody asked for.

**Gaps in a literal reading, stated plainly.** Two mechanical points the message leaves unstated rather than unintelligible. First, `git branch -D {name}` fails if the agent is currently checked out on `{name}`; the agent must first switch back to the default branch, a step the message implies (it says to commit onto the default branch) but does not order explicitly. Second, if commits were already made on `{name}` beyond the default branch tip, `-D` would strand them; the sensible execution is to carry that work onto the default branch (the tree state, or the commits themselves) before deleting. In the common case the branch was created at the default branch's tip and `-D` loses nothing. No part of the message is unintelligible to me.

**Why it exists, as far as I can tell.** The harness's branch-first default is baked into every session's system prompt, so without local enforcement the agent will silently fork: work lands on a branch the user never asked for, the default branch and the branch diverge, and the user inherits merge and cleanup work. The office methodology names this explicitly ("the bar is the silent fork, not the branch") and treats commit-straight-onto-main as the local norm, with staged commits and pushes as work lands. A CLAUDE.md sentence stating the inversion competes with the system prompt and can lose; a hook that fires at the exact moment of violation, names the offending branch, and gives the remediation command is enforcement at the point of failure rather than advice at session start. It also self-limits: it prescribes deletion only when the branch was unasked for, preserving legitimately requested branches.

**What I would do on receiving it.** Recall whether the user's request or an approved plan mentioned branching. If it did, ignore the remediation clause and continue. If it did not (the usual case, since the hook fires on my own initiative), I would: switch back to the default branch, confirm the branch tip holds nothing beyond the default branch (carrying any commits over if it does), run `git branch -D {name}`, commit the turn's work onto the default branch, and only then resume the task. I would not ask the user first, and I would not narrate the correction beyond a brief status note.
